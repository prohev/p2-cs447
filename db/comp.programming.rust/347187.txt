<!-- SC_OFF --><div class="md"><p>Hey everyone,</p> <p>I could use some insight here. I&#39;ve been bashing my head against this brick wall for a while now without getting anywhere.</p> <p>For some background, for the last couple of years I&#39;ve been developing a TypeScript/Node.js library that allows communicating with wireless devices via a serial modem while also providing high level abstractions and business logic to make writing applications based on this library easy.<br/> I&#39;m now trying to create a Rust version of this to be able to run on more constrained devices, or even embedded systems.</p> <p>There are a few challenges I need to solve for this:</p> <ul> <li>The library needs to continuously listen to the serial port to be able to handle incoming frames</li> <li>The library needs to be able to autonomously perform repeated or scheduled actions</li> <li>The library needs an API for consumers to send commands, retrieve information, and handle frames that are destined for the application</li> <li>Command/task executions are highly asynchronous in nature, often including multiple round trips via the serialport to devices and back. So being able to use async internally would be greatly beneficial.</li> </ul> <p>In Node.js, this is easy - the event loop handles this for me.</p> <p>I&#39;ve had a first version of this running in Rust too, but it ended up being messy: multiple Tokio tasks running their own loops, passing a bunch of messages around via channels. Tons and tons of Arcs everywhere. Even the most simple tasks had to be async.</p> <p>I&#39;ve started reworking this with the sans-io pattern in mind. The API for interacting with the serial port now looks similar to the example at <a href="https://www.firezone.dev/blog/sans-io">https://www.firezone.dev/blog/sans-io</a>, where the consumer provides a serialport implementation and drives the state machine handing the interactions. This can happen purely sync or async - the consumer decides.
